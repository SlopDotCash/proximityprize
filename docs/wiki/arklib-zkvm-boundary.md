# ArkLib-to-Whole-zkVM Verification Boundary

ArkLib is a proof-system verification library. It can be a necessary part of a
verified zkVM stack, but it is not by itself a proof that a concrete zkVM
verifier accepts only correct VM executions.

This page records the final boundary theorem ArkLib is meant to support and
names the soundness obligations and binding/encoding conditions that must be
supplied by ArkLib or by adjacent projects.
The matching Lean template is
`ArkLib/ProofSystem/ZkVMBoundary.lean`.

## Final Claim Shape

The whole-zkVM claim should have this shape:

```text
If a concrete verifier accepts a concrete proof for public input x,
and the binding/encoding conditions of that call hold
  (the deployment performs exactly that verifier call, and every ArkLib
   statement/proof decoded from it is transcript- and commitment-bound to the
   concrete proof, with its statement preserved by any recursion layer),
then there exists a valid VM execution trace producing the claimed public output.
```

The conclusion is derived, not assumed. It follows by composing three soundness
implications, each an explicit obligation:

1. Implementation soundness: concrete acceptance (under the deployment condition)
   produces a decoded ArkLib statement, which encodes x, and a decoded ArkLib proof
   that the ArkLib verifier accepts.
2. Proof-system soundness: ArkLib acceptance of a bound proof (under the recursion
   condition) produces a witness of the arithmetized trace relation.
3. Arithmetization soundness: a witness of that relation for a statement that
   encodes x produces a valid VM trace for x.

The Lean template names the claim `WholeZkVMEndToEndClaim` and proves it from the
three implications (`wholeZkVMEndToEndClaim_of_soundness`). It also checks that the
implications have content: `not_wholeZkVMSoundness_of_acceptAll` shows that a
verifier accepting every proof cannot satisfy them at a public input with no valid
VM trace, once the binding/encoding conditions hold for one call there. An earlier
version of the template took VM validity as a premise of the claim, which made the
claim hold for every choice of predicates (audit L02, 2026-10-28).

The implications are deterministic and model no soundness error. A computationally
or statistically sound instantiation must put its good event (no commitment
collision, no Fiat-Shamir/BCS bad challenge) into `transcriptAndCommitmentBinding`
and bound the probability of the complement separately; that bound is another
external obligation.

## ArkLib Scope

ArkLib can own these parts of the final theorem:

- Interactive oracle reductions, protocol specs, and composition/lifting APIs.
- Proof-system soundness/completeness/knowledge-soundness for Sumcheck, FRI,
  STIR, WHIR, Binius, LogUp, RingSwitching, Spartan, Plonk, and related protocols.
- Commitment and oracle-query abstractions used by proof-system theorems.
- Fiat-Shamir and BCS transforms at the mathematical protocol/spec level.
- Coding-theory, proximity, list-decoding, and polynomial facts used by those protocols.
- Named residual APIs for trusted external paper assumptions that are not yet
  internally proved.

## External Boundary Items

A whole-zkVM project must supply these interfaces outside the ArkLib proof-system
core:

- VM instruction semantics, such as RISC-V or EVM semantics, and the public
  output convention.
- Trace model: step relation, registers, memory, nondeterminism, halting, and
  failure states.
- Arithmetization correctness: constraints exactly encode valid traces,
  lookups, range checks, memory consistency, and permutation arguments.
- Protocol binding: the ArkLib relation consumed by the proof system is exactly
  the arithmetized trace relation.
- Fiat-Shamir, BCS, commitment, transcript, random-oracle, and query-opening
  implementation equivalence to ArkLib specs.
- Concrete prover/verifier implementation equivalence to ArkLib executable specs
  or mathematical specs.
- Serialization and deployment boundary, including on-chain verifier correctness
  if deployed verification is part of the claim.
- Recursion and aggregation soundness when the zkVM uses recursive proofs.

## Named Guest-Program Provider

For the current roadmap, [`Verified-zkEVM/evm-asm`](https://github.com/Verified-zkEVM/evm-asm)
is the named provider for the guest-program and VM-semantics side of this boundary.
It should discharge the RV64/EVM execution semantics, bounded guest-program
correctness, public input/output, halt conventions, and zkVM codegen/integration
contract. ArkLib should not re-prove those VM facts; it should consume them
through a relation such as `GuestTraceRelation` or `ArithmetizedTraceRelation`.

The remaining cross-repo bridge is explicit: prove that the relation supplied to
ArkLib by the arithmetization layer is exactly the relation generated by the
`evm-asm` guest trace and public I/O boundary. In the Lean template, the soundness
direction of that bridge is the `arithmetizationSoundness` obligation, with
`vmExecutionValid` supplied by the VM semantics.

## Lean Interfaces

`WholeZkVMInterfaces` names the abstract objects crossing the boundary:

- `PublicInput`
- `ConcreteProof`
- `ConcreteVerifier`
- `ArkStatement`
- `ArkProof`
- `VmTrace`
- `ArithmetizationWitness`
- `RecursionArtifact`
- `DeploymentArtifact`

`WholeZkVMRelations` names the boundary predicates. They are data: choosing them
asserts nothing.

- `concreteVerifierAccepts`
- `implementationMatchesArkSpec`
- `arkVerifierAccepts`
- `arithmetizedRelation`
- `publicInputEncoding`
- `vmExecutionValid`
- binding/encoding conditions: `transcriptAndCommitmentBinding`,
  `recursionPreservesStatement`, and `deploymentPreservesCall`, bundled for one
  verifier call as `WholeZkVMRelations.BindingConditions`

`WholeZkVMSoundness` names the proof obligations. Each field is an implication:

- `implementationSoundness`
- `arkProofSystemSoundness`
- `arithmetizationSoundness`

The theorem template is deliberately abstract. A concrete zkVM should instantiate
the relations with real types and predicates, prove each field of
`WholeZkVMSoundness`, and establish the binding/encoding conditions for the calls
the claim should cover. The `Toy` namespace in the Lean file checks a two-input
instance: the verifier that accepts exactly the valid input satisfies the
obligations, while the accept-all verifier satisfies neither the obligations nor
the end-to-end claim.

## Milestone Mapping

Existing ArkLib milestone issues should be read as discharging only parts of
`WholeZkVMSoundness` or of the binding/encoding conditions:

| Lean field | ArkLib-facing work |
|---|---|
| `arkProofSystemSoundness` | Soundness/completeness/knowledge-soundness for Sumcheck, FRI, STIR, WHIR, Binius, LogUp, RingSwitching, Spartan, Plonk, and related composition lemmas. These theorems are probabilistic; they give this deterministic implication only on the good event in `transcriptAndCommitmentBinding`. |
| `transcriptAndCommitmentBinding` | BCS, Fiat-Shamir, commitment, Merkle, KZG, random-oracle, query-opening, and transcript-binding work, including the probability bound for the complement of the good event. |
| `implementationSoundness` | Future executable-spec / extracted-code / hand-written-verifier equivalence work. |
| `arithmetizationSoundness` | Constraint-system and protocol-binding work, plus external arithmetization repos. |
| `vmExecutionValid` | External VM semantics projects; this is the predicate `arithmetizationSoundness` must reach. |
| `deploymentPreservesCall` | External serialization and on-chain verifier projects. |
| `recursionPreservesStatement` | Recursive-proof and aggregation projects when used. |

## Non-Claim

Finishing ArkLib is necessary but not sufficient for total zkVM verification.
Even a fully green ArkLib proof-system library would still need the VM,
arithmetization, implementation-equivalence, deployment, and recursion links
above before anyone can claim an end-to-end verified zkVM.
